The Axiom layer, on the real menu

These eleven are not a demo. They are roblox external/ui/menu_ui.cpp — the host application's menu — rendered by tools/menu_shots.cpp against stub platform callbacks, through the same software rasteriser. Because the layout file touches no Win32 and reads no process memory, the picture below is what the overlay draws, which is the only practical way to review a grid change without the game running. Labels are tracked caps because the widgets shout them; notes and hints are ordinary sentences, because a paragraph in caps is unreadable. The last few are states rather than pages — the ones a page loop cannot reach, because they need a setting and a runtime value to say something in particular together.

The filing rule for the pages, after a pass that moved things onto the tab that owns them: a setting lives where the decision is made, and a tab that borrows it says so in the group name. Which is how the hitbox expander ended up on the aimbot page, the inventory checker and the blacklist's ESP switch on visuals, every bind alone on the keybinds tab, the flight latch phrased like the aimbot's, and two of the duplicate switches gone. The rail counts moved with the settings they count, because a number that stays behind starts lying about its own tab.

The next pass took the same rule to the camera: FOV is how much of the screen you see and freecam is the point of view you see it from, so both moved to visuals and the movement page is now only the writes that move your character — which it shares into two groups, one for how it moves and one for how it arrives somewhere. That pass also moved filing from taste to test: the menu exposes HasGroup("page/name"), so the headless harness asserts that visuals owns the camera and that movement no longer owns a view group. A screenshot of the page a card moved to looks correct either way; only the old tab can say whether it let go.

Nine palettes, two knobs, one frame

The page loop above can only ever shoot the default theme, which is exactly the blind spot a theme system needs closed: a light preset that is only light in its own token names, a contrast knob that washes text out instead of hardening it. So the harness walks the same table the theme page offers — all nine — and asserts two things in numbers rather than by eye: that the ink sits on the correct side of its surface for the preset's polarity, and that text on panel clears 4.5:1 (3:1 for the dim label step). The three pictures here are the ones worth a look; the frames after them are the settings that change the window's structure or its material rather than its hue, which is where a layout actually breaks and where a colour-only review would miss it.

The material layer, on one switch

Ten dials is the right amount of control and the wrong amount of work for “can you turn that off”. Material::polish is the master multiplier: it folds into the ten strengths once, when a palette is installed, so every draw site simply reads 0 and draws nothing — no sheen, no bloom, no frost ring, no travelling band, flat surfaces. What it deliberately does not touch is animate / speed (freezing movement and removing shine are two questions) and the values you dialled in: the sliders keep their numbers, so the same picture with the switch flipped back on is the material you tuned, to the digit — which is asserted, both ways, by build/menu_shots. Dragging one of those sliders while polish is off turns polish back on, because wanting the dial is the only reason to reach for it. The two frames share a layout on purpose: the three groups above material are closed so the switch is at the top of the shot, which is also the collapsed-group contract, visible.
